# Employee Portal & Proposal Tracker — local setup and how logins work

Branch: `intern`. This is for anyone (e.g. a co-worker) who needs to run the
site locally and get exactly the same behaviour.

## 1. Run it locally

```bash
git clone https://github.com/avinash1425/gcoman-insight-design.git
cd gcoman-insight-design
git checkout intern
npm install
# put the .env.local file you were given (see step 2) in the project root
npm run dev        # → http://localhost:8080
```

## 2. The `.env.local` file (NOT in git)

`.env.local` points the site at the shared **test** Supabase project
(`dugllvupvcfdpddktrbt`). It is git-ignored on purpose, so get a copy from
the project owner over a private channel. Never commit it. It contains:

```
VITE_SUPABASE_PROJECT_ID=...
VITE_SUPABASE_URL=...
VITE_SUPABASE_PUBLISHABLE_KEY=...
VITE_TURNSTILE_SITE_KEY=...      # may be blank
```

Without it the marketing pages render, but login, admin and every form fail.

Everyone on the team uses the same test database, so employees added by one
admin are visible to everyone. The database changes listed in section 4 are
already applied to the test project (the six `20261127…` files on 2026-11-27,
through `supabase/APPLY_ALL_2026-11-27.sql`). `.env.db.local` (database password, also git-ignored) is only
needed by whoever applies migrations.

`supabase/functions/mcp/index.ts` is regenerated by the dev server and shows
up as modified after `npm run dev`. Don't commit that change:
`git checkout -- supabase/functions/mcp/index.ts`.

## 3. How logins work

There is **one** login page: `/login`. Where you land depends on the account:

| Account | Lands on |
|---|---|
| Website admin (has the `admin` role in `user_roles`) | `/admin` (counts as Super Admin: can do everything) |
| Active employee | the Employee Portal, `/portal` |
| Disabled employee | stopped with "Account disabled" |
| Any other website account | the homepage |

Proposal Tracker access is a **switch on the employee** (Employees → Add / Edit).
People with it on land on `/portal` like everyone else and open the tracker from
there. The tracker's profile menu has a link back to the portal.

### Roles (exactly four)

| Role | How you get it | What it gives |
|---|---|---|
| Super Admin | being a website admin (Settings → People) | everything |
| Admin | assigned by a Super Admin | website leads, Employees, Attendance, Leave; can give the Manager role; can view the rest of Settings |
| Manager | given by a Super Admin or Admin, and automatic when someone reports to you | "My team", team leave approval, team reports and messages |
| Employee | automatic for every active employee | the Employee Portal |

Only a Super Admin can reset the password of, disable or delete an Admin.

Every rule is checked in the database (`rbac_*` functions), not only hidden
in the screens.

### Managing employees (admin)

Admin dashboard → **Employee Portal → Employees**:

- **Add employee**: Employee ID (GC001, GC002… suggested), name, email,
  temporary password (↻ generates one), department, designation, phone,
  joining date, who they report to, the Admin role, and the Proposal Tracker
  switch (tracker code optional: the next free one is used), employment type and
  work location. The login works
  immediately. A ready-to-send message with
  the credentials appears once; send it yourself (the system sends no email).
- **Edit**: everything except the email (the login). A Super Admin changes
  the email in Settings → Users & Roles → Change email.
- **Reset password**: sets a new temporary one; the old one stops working.
- **Disable / Enable**: a disabled employee is signed out and cannot sign in.
- **Delete**: removes the employee and their login permanently.

Passwords: 8+ characters with an uppercase letter, a lowercase letter and a number.

### Employees' own passwords

The password the admin sets (on Add or Reset password) is **temporary**. At
the first sign-in the portal (or tracker) shows "Choose your own password"
and won't open until they set one. After that they can change it any time
under **My profile** (portal) or the tracker's profile menu → **Change
password**. The admin's list shows "Temporary password" until then.

### Attendance

Rules (Oman time; stored in the `attendance_settings` table, one row):

| Rule | Value |
|---|---|
| Office hours | 9:45 AM – 7:00 PM |
| Late | first punch-in of the day after 10:00 AM |
| Day status | under 4 h worked = Absent · 4 h+ = Half day · 4 h+ and worked until 7:00 PM = Present |
| Automatic punch-out | 8:00 PM (a session started after 8 PM closes at midnight) |
| Weekly off | Friday |

- **Employees** (portal), as in Zyllo: the portal is open only while punched in.
  Signing in without an open session (a new day, or after punching out), and
  punching out itself, show the punch-in screen with the last punch out. This
  applies on weekly off days, holidays and leave too (punching in then records
  attendance for that day). The other choice is Sign out; people with admin pages
  can open the admin panel. Roles without "Punch in / out" are not asked.
  **Attendance** shows a month calendar with totals (present, half day, absent,
  leave, late, hours) and the punch list, and lets them request a correction
  (today or the last 30 days, one pending request per day, no future or
  overlapping times).
- **Admin** → Employee Portal → **Attendance**: Daily (who is in / out / not
  in), By employee (month), Late, Missed punch-out, and Corrections
  (approve, or reject with a reason). Punch times are never edited directly;
  they change only through an approved correction.
- Forgotten punch-outs are closed at 8:00 PM the next time anyone opens
  attendance (no scheduled job needed; the result is the same).

### Leave

- **Leave types** (admin → Leave → Leave types; add more or change days any
  time): Casual 12, Sick 12, Emergency 6 days a year, Unpaid (no limit). All
  allow half days (single date only).
- **Holidays**: the admin enters them (Leave → Holidays). Weekly off days and
  holidays are never counted as leave. Adding or removing a holiday recounts
  any leave covering that date automatically.
- **Approval**: with a manager — manager reviews → admin approves → manager
  gives final approval. Without a manager the admin decides alone. The admin
  can act in place of the manager. Rejecting needs a reason. Nobody decides
  their own request. The employee can cancel until someone has approved.
- **Balances**: pending requests count against the balance. The admin can
  change one employee's days for a year (Leave → Balances, click a number).
- On a holiday or a full day of approved leave the punch-in screen is not shown.
- **Screens** (as in the Zyllo portal): portal → Leave has year buttons, balance
  cards, the apply form (live day count, First / Second half, the reporting
  manager set by the admin), company holidays and history; managers get a **Team
  requests** tab. Admin → Leave has status filters with each request's balance
  and a feedback box, balances with "Reset to default", leave types and a holiday
  table.

### Daily work report

- **Employees** (portal → Daily report): write "What did you work on today?"
  (required) and optionally pending work or blockers, for today or the last 7
  days. Save a draft, then submit. Submitted reports are locked unless sent back.
- **Review**: the reporting manager (portal → Daily report → Team reports) or an
  admin (admin → Daily Reports) marks it reviewed, or sends it back with a
  comment. Without a manager it goes to the admin. Nobody reviews their own.
- Admin → Daily Reports shows each day's submitted and missing reports, and all
  reports waiting for review. Data access for "Daily reports" is set per role.

### Notifications

- Portal → Notifications has three tabs: **Inbox** (filter by All, Unread or
  type), **Send message** and **Sent** (who got it and how many have read it).
  Urgent ones also show as a banner until read.
- Created automatically for daily reports, leave steps, attendance corrections,
  project membership, new tasks and company documents.
- Messages: employees write to colleagues they choose (up to 100); managers can
  also message their whole team; admins can message everyone.

- **Reminders** (admin → Notifications → Reminders: on/off, Oman time, days,
  Send now): not punched in (10:00), late or due tasks (10:15), daily report
  missing (18:30) and still punched in (19:30); each once a day. pg_cron runs
  them every 5 minutes; without it they go out while the portal is in use.
- Also automatic: punch-in confirmation (a late first punch-in also goes to Admins and
  the reporting manager), missed punch-out, welcome message, reporting manager changes.

### Projects and tasks

- Admin → Projects: create projects, choose the team and project manager, add or
  delete tasks.
- Portal → My projects: tasks, status, updates. A late task needs a reason to be
  marked done. The daily report can list hours and work per project.

### Profile and documents

- Portal → My profile: how complete the profile is, read-only work details, and
  personal details, contact information, 1-3 emergency contacts and documents
  (PDF or image, 10 MB, up to 50, private `employee-documents` bucket) that the
  employee edits.
- Admin → Employees → the profile button: personal details (needs "Personal
  details") and documents (needs "Documents"). Documents added by the admin (for
  example a certificate) can't be deleted by the employee.

### Settings · Roles & Permissions (one place for all access)

Admin → Administration → **Settings** (tabs: Users & Roles, Roles &
Permissions, Audit log).

- **Users & Roles**: everyone who can sign in, with their roles. Click **Edit
  roles** and the role buttons open under that person, then **Save roles**. A
  Super Admin can switch Super Admin, Admin and Manager; an Admin can switch
  Manager only. Employee is automatic, and Manager is locked on while people
  report to the person. **Change email** (Super Admin only) changes the email a
  person signs in with; the password stays the same and they are signed out.
- **Roles & Permissions**: pick one of the four roles (they can't be added or
  deleted), then switch each action of each page on or off. Changes apply
  immediately; sensitive permissions ask for confirmation first.
- **Data access** per role: Employees / Attendance / Leave / Reports →
  no access · own · team (reporting line) · department · all.
- Personal **Allow / Deny** exceptions are no longer linked from the screens; only
  a Super Admin can change them.
- **Audit log**: every role, permission, scope, exception and Super Admin
  change with who, when, old → new.

Precedence: Super Admin → personal deny → personal allow → active roles →
**denied by default**. Everything is checked in the database (functions and
table policies), not only hidden on screen; screens refresh access every 30 s
and on focus. Safety: nobody changes their own access; non-Super-Admins can
only give permissions and data access they have themselves and never Settings
permissions; at least one Super Admin remains.

Not covered yet: Search Console / AR vs EN SEO / "Run check" / Zoho re-send stay
Super Admin only (their edge functions check the website admin flag and can
only change when republished). Proposal Tracker permissions arrive with step 4
(its data still lives in each browser).

**Adding a permission (developers):** add a row to `rbac_permissions` in a new
migration (key `module.page.action`, plus `grp`, `page`, `tab`, `action_label`,
`kind`, `sensitive`, `description`, `sort_order`), check it in the database
function or policy with `rbac_require('<key>')` / `rbac_can('<key>')`, and in the
screen with `useCan()('<key>')` or `<Can perm="<key>">`. It appears in Settings
automatically and nobody has it until it is granted.

Tests: `psql "$SUPABASE_DB_URL" -At -f supabase/tests/rbac_permissions_test.sql`
(runs in a rolled-back transaction; also
`daily_reports_test.sql` and `portal_extras_test.sql`). Rollback of the four-roles change:
`supabase/rollback/20261127090000_four_roles_down.sql` (run it before the older
`20261126180000_rbac_down.sql`).

## 4. Database changes

**To update another database (production):** back it up, paste the whole of
`supabase/APPLY_ALL_2026-11-27.sql` into the Supabase / Lovable SQL editor and
run it **once**. It is the six `20261127…` migrations as one transaction (all or
nothing) and ends with a table where every `ok` should be `true`. Publish the new
front end at the same time. It needs the `20261126…` migrations already applied.

| Migration | What it does |
|---|---|
| `20261126120000_proposal_engineers.sql` | first engineer accounts (superseded) |
| `20261126130000_engineer_change_password.sql` | engineers choose their own password (superseded) |
| `20261126140000_employee_portal_foundation.sql` | `employees` table, roles & permissions (`rbac_*`), employee admin functions; moves engineers into `employees` (same ids) and drops `proposal_engineers` |
| `20261126150000_attendance.sql` | attendance: settings, punch sessions, correction requests, `att_*` functions |
| `20261126160000_leave.sql` | leave: types, per-employee allowances, holidays, requests + approval chain, `leave_*` functions; attendance learns about holidays/leave |
| `20261126170000_settings_roles.sql` | Settings: custom roles, role permissions, user roles, `rbac_admin_*` functions (no ready-made admin roles) |
| `20261126180000_rbac_core.sql` | Roles & Permissions engine: hierarchy, role active flag, personal overrides, data scopes, audit log, full catalogue, Settings functions |
| `20261126180100_rbac_enforcement.sql` | Data scopes inside Employees/Attendance/Leave functions and policies; finer employee/leave permissions; website & leads data moved to permissions |
| `20261127090000_four_roles.sql` | Four fixed roles (adds Admin), Proposal Tracker becomes a per-person switch, custom roles removed (holders keep the same access as personal permissions) |
| `20261127100000_admin_change_email.sql` | "Change email" in Users & Roles |
| `20261127110000_daily_reports.sql` | Daily work report: `work_reports`, `report_*` functions, permissions |
| `20261127120000_notifications.sql` | Notifications and messages |
| `20261127130000_projects.sql` | Projects, tasks, updates; project entries in the daily report |
| `20261127140000_profile_documents.sql` | Personal details, emergency contacts, documents and their private storage bucket |
| `20261127150000_leave_half_day_session.sql` | **NOT yet applied.** A half day is the first or the second half (run through `supabase/APPLY_NEW_2026-11-27.sql`) |
| `20261127160000_reminders.sql` | **NOT yet applied.** Automatic notifications and scheduled reminders; pg_cron job `portal-reminders` (run through `supabase/APPLY_NEW_2026-11-27.sql`) |

Apply them in this order on any other database (production included).

## 5. Known limits (prototype)

- **Proposal data (RFQs, tasks, follow-ups, approvals, daily updates) is still
  stored in each browser's localStorage**, not the database. Two people on
  different machines do not see each other's proposals yet. Logins and the
  engineer list *are* shared (database).
- "Forgot password?" relies on email, which isn't configured on the test project.
- Production: the migrations above have only been applied to the **test**
  project. They must be applied to the production database before this ships.
- Not built yet: moving proposal data into the database, scheduled reminders
  (`pg_cron` is available on the test project but not enabled), an admin inbox,
  and emailing daily reports (needs an email service).
- Tests for the new features: `supabase/tests/daily_reports_test.sql` and
  `supabase/tests/portal_extras_test.sql`.
